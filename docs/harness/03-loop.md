# 03. 구현 루프 — 몇 번까지 시도하고 언제 멈추는가

> 작성일: 2026-11-25
> 루프 규칙의 원본은 이 문서다. [SSOT](01-ssot.md) §4는 검증과의 경계만 선언한다.
> 사람이 무엇을 결정하는지와 그 결정을 받는 절차는 [04-decision.md](04-decision.md)가 원본이다.
> 이 문서는 그 결정이 **시도 횟수에 무엇을 하는지**만 정한다.
> 이 문서의 변경은 사람이 한다 (SSOT §0 보호 정책). 시도 횟수의 원본은 **그 작업 Issue의 코멘트**다.

---

## 1. 핵심 규칙

**세는 법**

- **LOOP-1** 시도 1회 = 구현부터 `python scripts/verify.py` **실행까지**다. `verify.py`를 한 번 돌리면 결과와 무관하게 그 시도는 끝난다. `verify.py` 이전의 수정(린트 · 타입 오류 정정 · 개별 `pytest` 확인 포함)은 전부 같은 시도 안이다.
- **LOOP-2** 시도가 끝나는 방식은 둘뿐이다 — ① `verify.py` 실행(통과 · 실패) ② `NEEDS_HUMAN` 중단(`LOOP-6`). 사람 구간의 복귀(`LOOP-13` · `LOOP-14`)는 시도를 끝내지 않는다. 복귀는 다음 시도 번호를 여는 ⊕1이고, 그 시도는 다음 `verify.py` 실행이나 중단으로 끝난다.
- **LOOP-3** 시도 상한은 그 작업 Issue의 §6이다. 기본값은 M=3이고, 큰 작업도 최대 5다. 5를 넘게 필요하면 상한을 늘리지 말고 Issue 분할을 제안하며 `NEEDS_HUMAN`을 선언한다. 상한을 다 쓰고도 종료 조건을 채우지 못하면 멈추고 `NEEDS_HUMAN`을 선언한다.
  **경계:** 마지막 시도(N=M)가 통과한 뒤 반려되면 구현하지 않고 `중단(상한 소진)`으로 기록한다. 반려는 ⊕1이므로 N+1이 M을 넘기 때문이다.
- **LOOP-4** 시도 횟수의 **원본은 Issue 코멘트**다. 세션 컨텍스트 · 대화 · 작업 트리 · PR은 원본이 아니다. 세션이 끊기면 다음 세션은 Issue 코멘트의 마지막 시도 번호부터 이어간다. 코멘트가 없으면 0회로 본다.
- **LOOP-5** 시도가 끝날 때마다 통과 · 실패와 무관하게 Issue 코멘트를 남긴다 (§3 양식). 코멘트가 없는 시도는 다음 세션에 없는 것과 같다.

**멈추고 다시 세는 법**

- **LOOP-6** (중단) `NEEDS_HUMAN` 중단은 **실패와 똑같이 시도 1회를 쓴다** — `verify.py`를 돌리지 않았어도 센다. 멈추는 것은 공짜가 아니다. 무엇이 중단 사유인지는 [04-decision.md](04-decision.md) `DEC-1`이 정한다.
- **LOOP-7** (초기화) 사람이 **판단 확정**을 주면 시도 횟수는 0으로 초기화된다. 상한도 처음부터 다시 센다. 기준이 명확해졌으므로 그 전의 시도는 다른 전제 위에서 돈 것이다.
- **LOOP-8** (종료) 사람이 **요구사항 변경**을 알리면 이 루프는 그 자리에서 끝난다. 남은 시도와 상한은 의미를 잃고, 시도 기록은 종료 시점까지로 닫는다. AI는 스스로 재개하지 않는다.
- **LOOP-9** → [04-decision.md](04-decision.md) `DEC-4` (완료 판정). **루프의 끝은 완료가 아니다.**

**사람에게 넘기고 돌아오는 법**

- **LOOP-10** (턴 넘김) 로컬 `verify.py`가 통과하면 턴을 사람에게 넘기고 기록을 남긴다. 넘기는 것 자체는 시도를 쓰지 않는다(⊕0). **PR은 필수가 아니다** — 사람 구간을 굴리는 수단일 뿐이다. PR을 연다면 로컬 `verify.py`가 통과한 뒤에 열고, 본문에는 `Closes #<번호>`와 "시도 기록은 그 Issue 코멘트"만 적는다 (§5).
- **LOOP-11** 같은 커밋에 대한 로컬 `verify.py`와 CI `verify`는 **한 시도**다. 시도는 실행 횟수가 아니라 **판정받은 코드 상태**를 센다.
- **LOOP-12** (대기) 사람 구간에 머무는 동안 시도는 소모되지 않는다. 마지막 기록이 「사람 차례」면 다음 세션은 사람 차례로 보고 새 시도를 시작하지 않는다. 사람이 **승인**을 주면 루프는 거기서 끝난다.
- **LOOP-13** (복귀) 사람이 **반려**를 주면 ⊕1로 기계 구간에 복귀해 다시 구현한다. 반려인지 요구사항 변경인지는 `DEC-9`가 가른다.
- **LOOP-14** (CI 실패) 같은 커밋 그대로 **re-run을 한 번** 해본다. re-run이 통과하면 환경 문제였으므로 시도를 쓰지 않고(⊕0), 또 실패하면 코드 문제로 보고 ⊕1로 복귀한다. 원인을 주관으로 가르지 않는다. 새 커밋 때문에 이전 실행이 취소된 것(`cancel-in-progress`)은 실패가 아니다.
- **LOOP-15** (출구) merge 없이 PR이 닫히면 시도 횟수는 그대로 남고 AI는 스스로 재개하지 않는다. merge · 승인의 권한은 `DEC-5`다.

**보류 · 진행 표시 · 실패 코드 · 재작업**

- **LOOP-20** (커밋 보류) 사람이 커밋 · 푸시 보류를 지시하면 AI는 커밋 · 푸시 · PR을 하지 않는다. `보류 · 커밋` 코멘트를 남기고 기준은 `uncommitted`로 적는다. 이 기록은 시도를 쓰지 않는다(⊕0).
- **LOOP-21** (진행 표시) 시작할 때 `진행 중 · 세션 <식별자>` 코멘트를 남기고, 턴을 넘기거나 멈추거나 끝낼 때 `진행 닫음` 코멘트를 남긴다. 닫히지 않은 `진행 중` 코멘트가 마지막이면 다른 세션은 시작하지 않고 사람에게 확인한다(⊕0).
- **LOOP-24** (실패 코드) 실패한 시도의 코드는 **이어서 고친다**. 판단 확정(`LOOP-7`)으로 초기화될 때만 사람이 되돌림 여부를 함께 지정한다.
- **LOOP-22** (재작업) 상태가 `CLOSED`(승인 완료)인 Issue에 재작업 지시가 오면 **새 Issue**로 한다. 새 Issue 본문에 `Follow-up of #N`을 적고 6개 항목은 사람이 채운다. 시도는 0부터 센다.
- **LOOP-25** (초기화 상한) 같은 Issue에서 판단 확정은 **2회까지**다. 3번째 판단 확정이 필요하면 분할을 알리는 신호로 본다 (§7).

## 2. 검증 · 사람 · 루프의 책임 분리

| | 검증 ([02-verification.md](02-verification.md)) | 루프 (이 문서) |
| :--- | :--- | :--- |
| 무엇을 보는가 | 변경한 코드 | 작업의 진행 |
| 수단 | `python scripts/verify.py` 한 줄 | Issue §6 상한 · Issue 코멘트 |
| 결과 | 통과 · 실패 | 계속 · 중단(`NEEDS_HUMAN`) · 종료 · 사람 차례로 넘김 |
| 모르는 것 | 몇 번째 시도인지 · 지금 누구 차례인지 | `verify.py`가 어느 단계에서 무엇을 검사하는지 |

**검증은 판정만 하고 멈출지는 정하지 않는다. 루프는 판정의 내용을 다시 따지지 않는다.**
`verify.py`가 실패했는데 루프가 "이 실패는 무시해도 된다"고 판단하면 검증 관문이 사라진다 (`VER-3`).

사람 구간에서 내려진 결정은 [04-decision.md](04-decision.md)가 **네 이름**으로 분류해 루프에 건넨다.

| 사람의 결정 (`04 DEC-9`) | 루프의 처리 |
| :--- | :--- |
| 승인 | 루프 종료 · 지시 대기 (`LOOP-12`) |
| 반려 | ⊕1 복귀 (`LOOP-13`) |
| 판단 확정 | 초기화 0/M (`LOOP-7` · `LOOP-25`) |
| 요구사항 변경 | 루프 닫힘 (`LOOP-8`) |

## 3. 시도 기록 — Issue 코멘트

세션 밖에 남는 유일한 상태다. 시도가 끝나거나 턴이 바뀔 때마다 하나씩 이어서 단다.
AI는 Issue 본문을 고치지 않는다 — 기록도 제안도 코멘트로 한다 (SSOT §0 보호 정책).

### 시도 코멘트

```markdown
### 시도 N/M · 통과 | 실패 | 중단(NEEDS_HUMAN) | 중단(상한 소진)
- 기준: <커밋 sha | uncommitted | PR #N · sha>
- verify: 로컬 통과 · CI 통과 | 실패(<멈춘 단계>) | 실행 안 함
- 한 일:
  - <파일 경로> — <무엇을 왜>
- 사람 판단이 필요한 것: 없음 | <내가 스스로 정한 것까지 전부>
- 다음 시도에서 할 것: 없음(종료) | <내용>
```

### 진행 중 · 보류 코멘트 (`LOOP-20` · `LOOP-21`)

```markdown
### 진행 중 · 세션 <식별자>
- 시각: <YYYY-MM-DD HH:mm>
- 기준: <sha | uncommitted>
- 시도 N/M 부터 이어감 (N = 마지막 시도 번호)
```

```markdown
### 진행 닫음 · 세션 <식별자>
- 사유: 턴 넘김 | 멈춤(<중단 종류>) | 종료
```

```markdown
### 보류 · 커밋
- 사유: 사람 지시 (커밋 · 푸시 · PR 하지 않음)
- 기준: uncommitted
- 작업 트리: <변경 파일 목록>
```

### 턴 넘김 · 복귀 코멘트

```markdown
### 사람 차례 · <PR #N | PR 없음>
- 기준: <sha> · 시도 N/M 까지 씀
- 사람이 할 것:
  - (수동) 종료 조건 <C번호> — <어디서 무엇을 보면 되는지>
  - 리뷰 · CI 확인 후 merge · 승인 (`DEC-4`)
```

```markdown
### 복귀 · <PR #N | PR 없음>
- 사유: 요구사항대로 안 됨 | CI 실패(<단계>) · re-run도 실패
- 처리: ⊕1 → 시도 N+1/M
```

사람의 승인 · 반려 · 판단을 적는 **「사람 판단」 코멘트 양식은 [04-decision.md](04-decision.md) §3**에 있다.

## 4. 세션 복구 절차

작업을 이어받을 때 이 순서로 읽는다.

1. **Issue 본문** — 종료 조건 · 건드리면 안 되는 것 · §6 상한 (개별 작업의 SSOT)
2. **Issue 코멘트** — 뒤에서부터 읽는다. 마지막 코멘트가 **턴**을 정하고, `판단 확정` 코멘트가 있으면 **그 뒤의 시도만** 센다. 코멘트가 없으면 0회.
3. **턴이 사람이면 손대지 않는다.** 아래 표로 판정한다.
4. **`기준` 줄** — 커밋이면 그 sha, `uncommitted`면 작업 트리의 diff, `PR #N`이면 그 PR을 읽는다.
5. **남은 시도 = M − N.** 0이면 새로 시도하지 않고 `중단(상한 소진)`으로 사람에게 넘긴다.
6. 이어서 하기 전에 `python scripts/verify.py`를 **먼저 돌리지 않는다** — 그 자체로 한 시도를 쓴다 (`LOOP-1`).

| 마지막 코멘트 | 턴 | 다음 행동 |
| :--- | :--- | :--- |
| 없음 · `시도 N/M · 실패` · `복귀` · `사람 판단 · 반려` | AI | 남은 시도 확인 후 구현 |
| `시도 N/M · 통과` | AI | 턴을 사람에게 넘긴다 (원하면 PR) |
| `사람 판단 · 판단 확정` | AI | 초기화 — 1회차로 구현 (`LOOP-25` 확인) |
| `진행 중 · 세션 …` (닫는 코멘트 없음) | **사람** | 시작하지 않고 사람에게 확인 (`LOOP-21`) |
| `보류 · 커밋` | **사람** | 지시가 바뀔 때까지 커밋 · 푸시 · PR 금지 (`LOOP-20`) |
| `사람 차례` · `사람 판단 · 승인` · `사람 판단 · 요구사항 변경` · `중단(…)` · `종료(…)` | **사람** | **손대지 않고 기다린다** |

> 코멘트와 작업 트리가 어긋나면(예: 코멘트는 실패인데 트리는 통과 상태) 판단하지 않고 사람에게 확인한다 (`DEC-1` ⑤ · `LOOP-6`).

## 5. PR과 CI

| 시점 | 무엇을 하는가 | 카운트 |
| :--- | :--- | :--- |
| **진입** | 로컬 `python scripts/verify.py` 통과 후에만 PR을 연다 | ⊕0 |
| PR 본문 | `Closes #<번호>` + "시도 기록은 그 Issue 코멘트" 한 줄 | — |
| **CI** | `.github/workflows/verify.yml`이 로컬과 동일한 `python scripts/verify.py` 실행 | 같은 커밋이면 ⊕0 (`LOOP-11`) |
| CI 실패 | 같은 커밋 그대로 **re-run 1회** → 통과면 환경 문제 (`CI 통과(re-run)`) | ⊕0 |
| CI 재실패 | 코드 문제로 본다 → `복귀` 코멘트 후 기계 구간 복귀 | **⊕1** |
| **LLM 리뷰** | CI 통과 뒤의 자문 ([04-decision.md](04-decision.md) §3) | ⊕0 |
| **출구** | merge · 승인은 사람 (`DEC-5`). merge 없이 닫으면 `중단(사람이 PR 닫음)` | ⊕0 |

## 6. 알려진 빈틈

- 코멘트 양식 오타는 `scripts/log_attempt.py`로 방지할 수 있으나, 코멘트 등록 호출 자체를 빠뜨리는 것은 자동 강제하지 못한다.
- 한 Issue를 여러 세션이 동시에 잡으면 `진행 중` 코멘트(`LOOP-21`)로 알릴 뿐 강제 락은 없다.
- PR 없이 진행하면 CI가 돌지 않아 Linux/Ubuntu 환경 차이가 드러나지 않는다.

## 7. 미정 · `NEEDS_HUMAN` 선언

아래 항목이 발생하면 AI가 임의로 처리하지 않고 `중단(NEEDS_HUMAN)`으로 멈춘다 (`LOOP-6`).

1. **`LOOP-25` 3번째 판단 확정** — 계속 진행할지 Issue를 분할할지 사람에게 확인한다.
2. **Issue §6 빈칸** — 템플릿 필수 항목이 비어 있으면 기본값 M=3으로 진행할지 멈출지 확인한다.
3. **`LOOP-24` 되돌림 여부의 기록 위치** — 판단 확정 코멘트에 별도 필드를 둘지 사람에게 확인한다.
4. **외부 변화(`main` 이동)로 생긴 CI 실패의 카운트** — `LOOP-14` 기준 ⊕1로 볼지 ⊕0으로 볼지 미정.
